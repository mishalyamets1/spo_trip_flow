# Материалы отчёта этапа II

Проект TripFlow — система учёта заявок на командировки. Материалы описывают реализованный код и выполненные проверки 29 октября 2026 года. Это техническая основа для оформления отчёта по образцу этапа I; скриншоты и индивидуальный вклад команды нужно добавить по фактической демонстрации.

## Практическая работа №5

### Структура репозитория

Создан npm-монорепозиторий: `apps/web` — Next.js/React, `apps/api` — Express, оба на TypeScript. `database` сохраняет SQL и миграции этапа I, `scripts` содержит команды окружения, `tests` — автоматические проверки, `docs` — контракты и инструкции. Зависимости зафиксированы в package-lock.json. README описывает запуск.

### Подключение к БД и первая операция

Express использует пул `pg`, схему trip_app и техническую роль trip_app_rw. Предметная операция `GET /api/expense-categories` возвращает категории расходов из существующей таблицы. Состояние процесса и БД проверяется маршрутами `/api/health/live` и `/api/health/ready`.

### Обработка HTTP

Справочник требует действующую сессию; успешный ответ — 200 и `{items:[...]}`. Нет сессии — 401. Ошибки ввода возвращаются структурированным JSON, ошибки соединения — 503. Бизнес-операции выделены из HTTP-обработчиков в модуль заявок.

### Каркас интерфейса

Подготовлены вход, список собственных заявок, форма и карточка. Страницы отображаются Next.js; запросы `/api` проксируются на Express. Браузер не имеет доступа к строке подключения БД.

### Локальный запуск и результат

`npm ci`, `make setup`, `make demo`, `make app`. Для DEMO_PASSWORD нужны отдельная настройка и первоначальное создание хэшей. Production-сборка и TypeScript-проверка прошли; локальная главная страница вернула HTTP 200. Адрес — http://localhost:3000. Подробности — `docs/runbook.md`.

## Практическая работа №6

### Схема сценария

Сотрудник входит, создаёт черновик с поездкой и сметой, сохраняет, при необходимости редактирует, отправляет заявку. Next.js → Express → PostgreSQL; после операции frontend получает актуальную карточку и версию.

### Элементы интерфейса

Реализованы форма поездки, добавление/удаление позиций сметы, сохранение черновика и отправка; список, карточка и история. Предусмотрены загрузка, пустой список, ошибки и обновление карточки при конфликте. Черновик заполняется обязательными полями исходной БД; незавершённая поездка не сохраняется.

### Хранение данных

Создание и редактирование изменяют поездку, заявку и смету транзакционно. Итог рассчитывается сервером в целых копейках. Отправка копирует маршрут, меняет статус на SUBMITTED, записывает submitted_at и историю в той же транзакции. Доступ к чужой карточке скрыт ответом 404; изменяющие операции проверяют роль и владельца.

### Проверки и исправления

API-тесты подтвердили создание, редактирование, конфликт версии, отклонение неправильных дат, недоступность чужой заявки и транзакционный откат при неверной категории расходов. Повторная отправка и изменение отправленной заявки возвращают 409. Исправлено представление `category_id`: оно возвращается строкой, чтобы сохранённая смета могла повторно отправляться формой без изменения типов.

### Выполненные требования

FR-01–FR-07 реализованы в учебном объёме. FR-08 в итоговом коде также имеет фильтры и пагинацию; развитие согласования FR-09–FR-11 описано в этапе III. Полноценное управление учётными записями и справочниками FR-12 пока отсутствует.

## Практическая работа №7

### Окружение

Docker Compose содержит db, api и web. Для приложений используется профиль app. Отличие от dev: frontend и backend собираются и работают в контейнерах; БД сохраняется в volume. Публичный хостинг не используется.

### Зависимости и настройки

Node.js 24, npm, PostgreSQL 16, golang-migrate. Имена переменных: POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_PORT, TRIP_APP_RW_PASSWORD, DATABASE_URL, APP_ORIGIN, API_PORT, COOKIE_SECURE, DEMO_PASSWORD. Значения рабочих секретов в материалы не включаются. API внутри Compose использует PGHOST, PGUSER, PGPASSWORD и PGDATABASE.

### Подключение БД и получение кода

Миграции запускаются владельцем, runtime — ролью trip_app_rw. В исходной рабочей папке не было Git-метаданных; порядок получения кода из командного удалённого репозитория необходимо дополнить его реальным адресом. Текущие команды выполняются из каталога проекта.

### Адрес и проверка

http://localhost:3000. Проверены HTTP 200 главной страницы, ready=200, вход через прокси Next.js, чтение исходной заявки с фильтром SUBMITTED и выход 204. Все контейнеры достигли состояния healthy. Полный цикл записи проверен отдельно API-тестами на временной БД.

### Ошибки подготовки окружения

При первом запуске тестового окружения SQL выполнялся без search_path и не находил users. Исправлено явным выбором схемы в каждой тестовой SQL-сессии. Ограничения локальной песочницы на Docker и npm были преодолены штатными запросами разрешений; это ограничения инструмента, а не дефекты приложения.

## Практическая работа №8

### Конфигурация и права

Приложения работают в контейнере от пользователя node. PostgreSQL опубликован только на 127.0.0.1; API наружу не публикуется. Backend работает под trip_app_rw. Автоматический тест подтвердил отказ 42501 на CREATE TABLE от этой роли.

### Перезапуск и связь с БД

Настроены restart unless-stopped, healthcheck и depends_on с service_healthy. Контейнеры пересоздавались без удаления volume; исходная заявка и история сохранились. Проверка контролируемого отказа и последующего восстановления описана в материалах этапа III.

### Защита

Пароли пользователей — scrypt с солью; сессии — случайные токены и HttpOnly cookie с серверным сроком действия. Изменяющие запросы проверяют Origin. Секреты находятся в окружении и исключены из образов и Git. Пароль роли БД настраивается отдельной командой provision вместо изменения старой миграции. HTTPS для публичного сетевого доступа ещё не настроен; стенд ограничен localhost.

### Логи и действия при сбое

Структурированные логи содержат requestId, метод, путь, HTTP-код и длительность. Ошибки соединения фиксируются без паролей и DSN. Диагностика: live → ready → логи api/db → восстановление подключения → повтор сценария.

### Протокол проверок

- Пересоздание контейнеров: ожидалось сохранение исходных данных; исходная заявка и две записи истории доступны после запуска.
- Запрос без сессии: ожидался 401; получен 401.
- Изменение с чужим Origin: ожидался 403; получен 403.
- DDL от trip_app_rw: ожидался отказ; получен 42501.
- Неправильные даты и отрицательные суммы: ожидался отказ; проверки валидации и CHECK прошли.
- Браузерная визуальная проверка: не выполнена, управление Chrome отклонено проверкой разрешений. Скриншоты и удобство работы нужно проверить вручную.
