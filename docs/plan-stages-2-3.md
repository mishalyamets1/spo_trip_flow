# План выполнения этапов II и III проекта TripFlow

План составлен 29 октября 2026 года по исходным файлам проекта, отчёту этапа I и заданиям практических работ №5–14. Это план будущей реализации. Запуск Docker, применение миграций и работоспособность БД при подготовке плана не проверялись.

## 1. Исходное состояние

В проекте подготовлены:

- PostgreSQL 16 в `docker-compose.yml`, volume данных и healthcheck БД.
- Схема `trip_app` из 11 таблиц в `database/migrations/000001_init.up.sql`: пользователи, роли, сотрудники, подразделения, поездки, заявки, категории расходов, смета, этапы согласования и история статусов.
- Обратные миграции и тестовый набор в миграции `000002_seed`.
- Команды запуска, миграций и SQL-проверок в `Makefile`.
- Запросы Q-01–Q-04 в `database/queries/check_queries.sql`.
- Отчёт этапа I с FR-01–FR-12, NFR-01–NFR-09, сценариями UC-01–UC-05 и распределением ролей.

В просмотренной папке отсутствуют код frontend и backend, зависимости Node.js, Dockerfile приложений, API, тесты приложения и Git-метаданные. Наличие общего удалённого репозитория по этой папке установить нельзя.

### Что учесть до реализации

1. В `users.password_hash` находятся `TEST_HASH_NOT_FOR_AUTH`. Реальный вход потребует хэшей и отдельной команды подготовки демонстрационных учётных записей.
2. В миграции `000001` пароль `trip_app_rw` задан литералом. `TRIP_APP_RW_PASSWORD` из окружения сейчас не управляет этой командой. Настройку пароля вынести в отдельный шаг подготовки окружения; уже применённые миграции не переписывать. Не передавать секреты через вывод Makefile или логи.
3. Контейнер БД публикует порт без привязки к localhost. Для локальной разработки привязать его к `127.0.0.1`, в тестовом Compose доступ к БД оставить по внутренней сети.
4. `DATABASE_URL` в примере рассчитан на backend на хосте. В контейнере backend должен подключаться к `db:5432`; для запросов явно использовать схему `trip_app` либо настроить `search_path`.
5. `make check` содержит SELECT-проверки Q-01–Q-04, но не проверяет ожидаемый результат автоматически. Q-05–Q-08 из отчёта в файле отсутствуют. Добавить проверки ограничений с ожидаемыми SQLSTATE и изоляцией ошибок через отдельные транзакции или SAVEPOINT.
6. `make reset` удаляет volume БД, а откат seed-миграции очищает данные таблиц. Эти команды нельзя использовать как обновление или восстановление рабочей учебной версии.
7. Ограничения БД не обеспечивают порядок согласования, обязательность комментария при отказе, актуальность суммы сметы и увеличение `version`. Это обязательные правила серверных сервисов и их тестов.
8. CHECK у заявки запрещает `CANCELED` с пустым `submitted_at`. Отмену черновика пока не вводить: FR-04 предусматривает его удаление. Если отмена понадобится, сначала уточнить семантику и подготовить миграцию.
9. В отчёте критерий первого показа включает решение согласующего, но сценарий согласования запланирован следующей итерацией. Поэтому результат этапа II обозначать первым рабочим срезом, а полный показ создания и решения проводить после этапа III.

## 2. Архитектура и границы версий

Сохранить стек отчёта: Next.js, React, TypeScript, Express, PostgreSQL. Сервер Express остаётся модульным монолитом. SQL и бизнес-операции выполняет только backend.

Планируемая структура:

```text
apps/web/                 страницы Next.js, формы, клиент API
apps/api/src/modules/     auth, requests, approvals, dictionaries
apps/api/src/db/          подключение к PostgreSQL и транзакции
packages/contracts/      общие структуры данных при необходимости
database/migrations/     существующие и новые миграции
database/queries/        контрольные SQL-проверки
tests/                   интеграционные и сквозные проверки
docs/api/                единый OpenAPI-контракт
docs/decisions/          решения о статусах, доступе и маршрутах
docs/stage-2/            материалы работ №5–8
docs/stage-3/            материалы работ №9–14
```

Этап II: вход сотрудника, собственные заявки, создание и изменение черновика со сметой, отправка одному согласующему, отображение статуса и истории. Интерфейс принятия решения пока не входит в этот срез. Выбор одного согласующего фиксируется конфигурацией учебного окружения; сервер проверяет его существование, активность и роль.

Этап III: очередь согласующего, утверждение и отклонение, последовательный маршрут из нескольких согласующих, конфликт версий, фильтры и пагинация, формализованный REST API, обновление и восстановление окружения.

FR-12 с интерфейсом администрирования оставить последующей итерации как Should. Финансовый специалист пока использует роль `APPROVER` на назначенном этапе, как предусмотрено отчётом.

### №10. Развитие существующей БД

### №11. Проектирование REST API

До расширения обработчиков создать единый `docs/api/openapi.yaml`. Небольшой контракт этапа II описать ещё перед №6, здесь расширить и привести к единому виду.

Планируемые ресурсы:

- `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`.
- `GET /api/expense-categories`.
- `GET /api/requests` с фильтрами статуса и периода и пагинацией.
- `POST /api/requests`, `GET /api/requests/{id}`, `PATCH /api/requests/{id}`, `DELETE /api/requests/{id}`.

- `GET /api/approvals` с выдачей только текущих доступных этапов.
- `POST /api/approvals/{id}/approve`, `POST /api/approvals/{id}/reject`.

Зафиксировать JSON-структуры поездки, сметы, заявки, решения и ошибки; формат дат, сумм и идентификаторов; передачу версии для изменяющих операций; сортировку и смысл фильтра периода. Коды: 200/201/204 для успешных операций, 400 для некорректного ввода, 401 без сессии, 403 при запрете операции, 404 для отсутствующего ресурса, 409 при конфликте версии или состояния, 503 при недоступности БД. Для чужих заявок выбрать и последовательно применять политику, не раскрывающую их содержимое.

Готовность: контракт содержит связь операций с FR, параметры, доступ, ответы и JSON-примеры минимум пяти операций, включая ошибки.

### №12. Реализация и проверка API

1. Реализовать очередь, утверждение и отказ в модулях Express; отделить HTTP-обработчики, бизнес-сервисы и SQL-доступ.
2. При отправке копировать маршрут в `approval_steps` в той же транзакции, что меняет заявку и историю. Если подходящего маршрута нет или согласующие недопустимы, не отправлять заявку.
3. Показывать в очереди только `PENDING`-этапы пользователя, у которых все предшествующие этапы утверждены. Само значение `PENDING` не означает, что этап уже доступен.
4. Решение принимать транзакционно с блокировкой или условным обновлением и проверкой версии; синхронно менять этап, заявку и историю. Проверять владельца этапа, порядок, статус, запрет самосогласования и комментарий отказа.
5. Доработать фильтры и пагинацию, UI очереди, карточку с этапами, кнопки решения и отображение конфликтов. Хотя полная интеграция отдельно рассматривается позднее в №21, этот небольшой интерфейс нужен для демонстрации выбранного сценария.
6. Проверить API и БД интеграционными тестами; выполнить два сквозных сценария в браузере: создание → два утверждения и создание → отказ.

Обязательные негативные случаи: чужая заявка; действие без роли; второй этап раньше первого; самосогласование; пустой комментарий; повторное и конкурентное решение; устаревшая версия; неверные даты и отрицательная сумма; сбой внутри транзакции.
