# Требования дополнения IV этапа

Дата: 12 ноября 2026 года. Дополнение к FR-01–FR-12 из этапов I–III. Выбранные функции развивают существующий TripFlow; PDF требует доработки проекта, но не предписывает именно отмену и архив.

## FR-13. Отмена до первого решения

Автор с действующей ролью EMPLOYEE может отменить свою заявку только в состоянии SUBMITTED, пока ни один её этап не получил APPROVED/REJECTED. Обязательны актуальная `version` и причина длиной 1–2000 символов после trim. Черновик по-прежнему удаляется отдельной операцией.

Критерии приёмки:

1. Успех возвращает карточку CANCELED, время и причину отмены; `version` увеличивается на один.
2. Все PENDING-этапы становятся SKIPPED, добавляется ровно одна запись истории. `submitted_at` сохраняется; `decided_at` не используется как время отмены.
3. Без сессии — 401; без роли — 403; чужая/несуществующая заявка — 404; неверное тело — 400; старая версия или недопустимое состояние — 409.
4. После первого решения отмена запрещена. При гонке отмены и первого согласования один запрос успешен, второй получает 409; частичных изменений нет.
5. UI показывает действие по серверному `can_cancel`, требует причину и подтверждение, отображает итог. Повторная отправка CANCELED не предусмотрена.

Проверки: `tests/helpers/stage4.ts`, браузерный сценарий B-01 в [отчёте](report.md).

## FR-14. Обработанные согласующим заявки

Согласующий с текущей ролью APPROVER видит собственные APPROVED/REJECTED-этапы, включая заявки, переданные далее или завершённые. Архив строится по назначениям `approval_steps`, без копирования заявок.

Критерии приёмки:

1. `/api/approvals` по умолчанию показывает только текущие ожидающие этапы. `view=processed` выбирает принятые пользователем решения; SKIPPED в этот список не входит.
2. Общий статус заявки отделён от собственного решения, даты и комментария. Одобрение менеджера не означает окончательного согласования заявки.
3. Доступны фильтр собственного решения APPROVED/REJECTED и границы периода поездки: начало не раньше `from`, окончание не позже `to`.
4. Списки имеют `total`, `page`, `page_size=20`; порядок стабилен. Обработанные сортируются по времени решения и id этапа по убыванию.
5. Вкладка, фильтры и страница находятся в URL. Из карточки можно вернуться к тому же списку. Отозванная роль закрывает очередь и доступ к назначенной чужой карточке/истории.

Проверки: тест 21 решения на двух страницах, разграничение пользователей и фильтры в `tests/helpers/stage4.ts`; браузерный сценарий B-02.

## Уточнения прежних требований

- FR-01: сессии PostgreSQL и cookie сохраняются; JWT не добавляется. Явный выход ведёт на `/login`, истечение сессии сохраняет безопасный адрес для повторного входа.
- FR-02: назначение на этап не заменяет действующую роль APPROVER при чтении чужой карточки.
- FR-09: очередь содержит только доступный сейчас этап; обработанные решения вынесены в отдельный список FR-14.
- FR-10/FR-11: порядок согласования, снимок маршрута и окончательное решение не меняются.
- NFR-02/NFR-06: отмена атомарна; согласованность полей отмены дополнительно ограничена CHECK в БД.
- FR-12, нагрузочные измерения, CI, публичный HTTPS и итоговый релиз не входят в это дополнение. План V этапа остаётся отдельным.
