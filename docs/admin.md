# Администрирование TripFlow

Реализация FR-12 и управления заявками: сотрудники, роли, маршруты, подразделения и категории расходов. Контракт 0.5.0, схема 8. Приложение и API сохраняют разделение на компоненты, контроллеры, сервисы и репозитории. Полная сверка критериев — в [проверке требований](requirements-audit.md).

## Первый запуск и вход

Для существующего стенда:

```bash
make backup
make migrate
make admin
make app
```

`make admin` создаёт первого администратора с почтой `ADMIN_EMAIL` (по умолчанию `admin@example.test`). Нужен `ADMIN_PASSWORD` длиной от 12 символов. На учебном стенде допустим fallback на существующий `DEMO_PASSWORD`. Пароль сохраняется как scrypt, в консоль не выводится. Существующие аккаунты и пароли команда не меняет. Если активный администратор уже есть, повторный запуск ничего не создаёт. Публичной регистрации ADMIN нет.

При настройке текущего локального стенда создан новый случайный `ADMIN_PASSWORD` в `.env`, поскольку ни ADMIN_PASSWORD, ни DEMO_PASSWORD не были заданы. Пользователи сотрудника, менеджера и финансиста не изменялись. Значение пароля не включается в отчёт и Git.

Вход: http://localhost:3000/login. Администратор с одной ролью ADMIN попадает в `/admin/employees`. При совмещении ролей доступны также личные заявки/согласование согласно правам. API проверяет актуальную роль на каждом запросе; административные транзакции повторяют проверку после получения блокировки.

## Сотрудники

`/admin/employees`: поиск по имени, почте и табельному номеру, фильтры подразделения/активности, страницы по 20 записей. Карточка содержит имя, почту, должность, подразделение, табельный номер, телефон, дату приёма, роли и активность. При создании задаётся начальный пароль; изменение пароля в интерфейс не включено.

Роли можно совмещать. Блокировка отключает вход и удаляет сессии. Снятие APPROVER/блокировка запрещены, если остаются ожидающие чужие этапы или назначения в шаблонах: сначала следует переназначить этапы и отредактировать маршруты. Собственную учётную запись администратора нельзя заблокировать, удалить или лишить ADMIN; также проверяется наличие другого активного администратора перед удалением/отключением ADMIN.

Изменение сотрудника проверяет `version`. Повтор старой формы возвращает 409 с предложением обновить данные. Дубли почты/табельного номера отклоняются; создание аккаунта, профиля, ролей и запись журнала выполняются одной транзакцией.

## Удаление сотрудника и его заявок

В карточке есть отдельное подтверждение: число заявок, причина, ввод табельного номера. Форма предупреждает, что восстановления в интерфейсе нет. Операция удаляет **все** заявки автора независимо от статуса, их сметы, поездки, этапы и историю; затем профиль, учётную запись, роли и сессии. API принимает актуальную версию профиля и `expected_request_count`; при изменившемся количестве требуется повторное подтверждение.

Чужие заявки сохраняются. Если сотрудник принимал решения в них, остаются статус, комментарий, дата и снимок имени. Ссылки на удалённый профиль становятся NULL. Миграция заполняет снимки имён и для старых решений/истории.

При ожидающих назначениях в чужих заявках или участии в шаблонах требуется выбрать активного APPROVER для замены. Замена не может быть автором затронутой заявки, уже участвовать в том же согласовании или повторяться в шаблоне. Передаются все ожидающие чужие этапы и назначения во всех шаблонах; версии затронутых заявок/маршрутов увеличиваются. Принятые решения не переназначаются.

Удаление, передача назначений и запись журнала атомарны. Ошибка откатывает всё. Блокировки заявок согласованы по порядку id; конкурирующие изменения могут вернуть 409, после чего нужно обновить экран. Работающие пользовательские данные при проверке удаления не удалялись: destructive-сценарии проверяются только в отдельной временной БД.

## Все заявки

`/admin/requests`: поиск по номеру/имени автора, фильтры подразделения, автора через query `employee_id`, статуса и периода поездки; страницы по 20. Карточка показывает смету, этапы и историю. Возврат сохраняет фильтры списка.

Действия:

- Отмена DRAFT/SUBMITTED/UNDER_REVIEW с обязательной причиной. Ожидающие этапы закрываются как SKIPPED; уже принятые решения остаются. APPROVED/REJECTED/CANCELED не меняются. Для отменяемого DRAFT в одном UPDATE устанавливается технический `submitted_at`, необходимый исходному CHECK для любого статуса кроме DRAFT; история прямо отражает DRAFT → CANCELED, без фиктивного события отправки.
- Замена согласующего первого ожидающего этапа в SUBMITTED/UNDER_REVIEW. Требуются причина и версия. Нельзя назначить автора или человека, уже участвующего в этом согласовании. Шаблон подразделения этим действием не меняется.

Свободного изменения статуса, редактирования утверждённой сметы, удаления отдельной чужой заявки и решения от имени согласующего в админке нет.

## Маршруты и журнал

`/admin/routes`: создание и редактирование маршрутов, активность, подразделение, выбор и порядок 1–20 согласующих. В подразделении может быть один активный маршрут. Участники — активные APPROVER без повторений. Подразделение существующего маршрута не меняется. Изменения шаблона не переписывают уже отправленные заявки. Запрет самосогласования при отправке сохраняется: для поездки самого руководителя нужен подходящий маршрут его подразделения.

`/admin/audit`: кто, когда, какой объект и по какой причине изменил. Отдельный `admin_audit_log` хранит создание/изменение/удаление сотрудников, отмены, переназначения и настройку маршрутов. В details записываются технические идентификаторы/счётчики и параметры действия; пароль и хэш туда не передаются. Имя администратора сохраняется даже после удаления его профиля. API удаления/редактирования журнала нет.

## Справочники

`/admin/catalogs`: подразделения и категории расходов. Можно создать значение, изменить название/код категории, отключить или включить его. Изменения проверяют версию и попадают в журнал администратора.

Используемое значение нельзя удалить: API возвращает 409, интерфейс показывает число связей. Отключение сохраняет старые связи, но скрывает категорию при новом выборе и запрещает новое назначение сотрудника/маршрута отключённому подразделению. Существующий черновик может сохранить уже использованную отключённую категорию; существующий профиль — своё подразделение. Поэтому исторические заявки не ломаются.

## API

Все пути ниже имеют префикс `/api/admin`, доступны только ADMIN и описаны в [OpenAPI](api/openapi.yaml). Изменения требуют JSON и допустимый Origin, как остальное приложение.

- `GET /metadata` — подразделения и активные согласующие.
- `GET/POST /employees` — поиск/создание.
- `GET/PATCH/DELETE /employees/{id}` — последствия удаления, изменение, удаление с заявками.
- `GET /requests`, `GET /requests/{id}` — все заявки и карточка.
- `POST /requests/{id}/cancel` — `{version, reason}`.
- `POST /requests/{id}/reassign` — `{version, approver_employee_id, reason}`.
- `GET/POST /routes`, `PATCH /routes/{id}` — маршруты; создание с version=0, изменение с текущей версией.
- `GET/POST /catalogs/{kind}`, `PATCH/DELETE /catalogs/{kind}/{id}` — `kind=departments` или `expense-categories`; изменение/удаление требует version.
- `GET /audit?page=1` — журнал.

Пример тела удаления:

```json
{
  "version": 3,
  "expected_request_count": 5,
  "replacement_employee_id": "8",
  "reason": "Сотрудник больше не работает в организации"
}
```

`replacement_employee_id` можно не передавать только при отсутствии зависимых назначений. Успех возвращает `{ "deleted_request_count": 5 }`. Типовые ошибки: 400 — вход/неподходящая замена, 401 — сессия, 403 — роль/Origin, 404 — объект, 409 — версия/изменившееся число заявок/конфликт назначений/уникальность. Ошибка содержит `error.message`; валидация также `error.fields`.

## Обновление и откат

Миграция добавляет версии профилей/маршрутов, снимки имён в этапах/истории, nullable ссылки на исторических участников с ON DELETE SET NULL и журнал администратора. BEFORE INSERT-триггеры заполняют снимки и для прежних SQL-писателей, не передающих новые поля. Для PENDING сохраняется CHECK наличия согласующего.

Сделана копия `backups/tripflow-2026-11-12T10-49-09.311Z.dump`. На восстановленной временной БД проверены up/down/up: старые строки/столбцы всех 14 таблиц совпали до/после, новые поля исключены из сравнения. Перед созданием администратора после рабочей миграции также подтверждено совпадение всех 14 старых таблиц. Доказательства — `output/admin/migration-check.json` и `live-migration-check.json`.

Down допустим только до удаления исторических участников; если остались NULL-ссылки, он отказывается работать. После использования новой функциональности нужен совместимый код либо согласованное восстановление backup, которое может потерять последующие изменения. `make reset` для обновления не используется.

## Проверка

`make test` создаёт и удаляет свою временную БД. Добавлены сценарии: запрет без ADMIN; создание и откат дубликата; версии профилей; блокировка и отзыв сессии; защита своего администратора; маршруты/снимки/повторы участников; чтение всех заявок; замена текущего этапа и запрет автора; последствия и подтверждение удаления; полное удаление собственных черновика/завершённой заявки; сохранение решения/имени/истории в чужой заявке; передача ожидающего этапа/шаблона; административная отмена после первого решения и для DRAFT; журнал без паролей/хэшей.

Результаты текущего запуска и браузерной проверки фиксируются в [verification.md](verification.md). CI, нагрузочные измерения и эксплуатационная проверка описаны в [V этапе](stage-5/report.md). Публичного развёртывания нет.
