# Как проверить V этап

Понадобятся Node.js 24, установленные зависимости (`npm ci`), Docker и подготовленная роль БД (`make setup`). Существующий `.env` сохранять. Не использовать `make reset`.

## Быстрая автоматическая проверка

```bash
npm run typecheck
npm run format:check
make test
npm run build
make monitor
```

Ожидается: 37 тестов без ошибок/пропусков, успешная сборка, live/ready=200. `make test` применяет миграции в своей временной БД и удаляет только её. `npm test` без TEST_DATABASE_URL пропускает интеграционные проверки, поэтому для полной проверки нужен именно `make test`.

Покрытие бизнес-модулей: `node scripts/test.mjs --coverage`. Последний результат — 97,69% строк services/repositories/validators. Это не покрытие всего frontend/API.

## Проверка кликами без изменения рабочих данных

```bash
make preview-checks
```

Дождаться сообщения о готовности и открыть **http://127.0.0.1:3105**. Рабочее приложение localhost:3000 продолжает работать отдельно. Не менять адрес на localhost: у стендов должны быть раздельные cookie.

В этом временном стенде у всех аккаунтов пароль **`TripFlow-checks-2026!`**:

- `admin@example.test` — администратор и третий согласующий;
- `maxim@example.test` — сотрудник;
- `manager@example.test` — первый согласующий;
- `finance@example.test` — второй согласующий.

Это специальные синтетические аккаунты; пароль администратора рабочего приложения берётся из `.env`, а не отсюда.

Проверить справочники:

1. Войти администратором → «Справочники».
2. Создать подразделение, изменить название, отключить его. Убедиться, что действия появились в журнале.
3. Переключиться на категории; создать категорию с кодом `CHECK_EXTRA`, отключить её. Сотрудник не должен видеть её среди новых вариантов сметы.
4. У используемого значения показано число связей, удаление запрещено. Удалять можно только специально созданное неиспользуемое значение этого временного стенда.

Проверить историю:

1. В «Все заявки» открыть карточку №2: три решения, включая «Этап 2: согласовано», присутствуют в истории по одному разу.
2. Для повторения полного процесса использовать уже отправленную №3. Поочерёдно войти менеджером, финансистом и администратором, открыть очередь и согласовать свой этап с разными комментариями.
3. После каждого решения история должна увеличиваться: после отправки 2 события, далее 3, 4, 5. После второго решения статус остаётся UNDER_REVIEW, но событие решения видно. После третьего — APPROVED.
4. Повторить чтение карточки на ширине 360 px через режим устройства DevTools. Проверить перенос текста и доступность действий.

Выйти из аккаунта при смене роли. Завершить стенд Ctrl+C в терминале: процессы и его временная БД удаляются, изменения этого стенда не сохраняются. Если процесс принудительно завершён системой, проверить оставшиеся `tripflow_test_preview_*` вручную; рабочую БД `tripflow` не удалять.

## Нагрузка и оптимизация

```bash
make benchmark-baseline
make benchmark
```

Запускать последовательно, без параллельной сборки/другого нагрузочного теста. Создаются отдельные БД с 10 000 заявок и 50 пользователями; каждый запуск выполняет прогрев и три серии по 1 000 запросов списка/карточки. Baseline исключает только индекс 000008. JSON с p50/p95, ошибками и EXPLAIN сохраняется в `output/stage-5/benchmark-before.json` и `benchmark-after.json`. Ожидается `nfr01_pass=true`, ошибок 0, p95 обеих операций не выше 2 000 мс. Время SQL и HTTP сравниваются отдельно.

## Миграции, резервная копия, отказ

```bash
make verify-upgrade FILE=backups/копия-схемы-6.dump
make verify-runtime
make monitor
```

Первая команда требует именно копию до V этапа: сравнивает старые поля 15 таблиц при up/down/up. Вторая создаёт свежую рабочую резервную копию, восстанавливает её в свою БД, сравнивает данные, читает карточку и вызывает отказ только этой копии. Ожидается live=200, ready=503 во время отказа и ready=200 после восстановления; requestId ошибки должен совпасть с журналом. Отчёты — `upgrade-check.json`, `runtime-check.json`.

`make monitor BASE_URL=http://localhost:3000` проверяет работающий стенд три раза. При любой ошибке exit code=1. Для сохранения: `MONITOR_OUTPUT=output/stage-5/monitor.jsonl make monitor`. JSON-логи API смотреть через `docker compose logs --tail=50 api`.

## CI и границы проверки

GitHub Actions запускается при push/PR и вручную. На странице Actions видны шаги форматирования, типов, БД, тестов и сборки; успешный запуск отдаёт архив сборки на 7 дней. Архив не содержит `.env` и backup и не заменяет установку зависимостей/настройку среды. Обновление рабочего стенда выполняется явно командой `make app` после миграции.

Проверки выше не подтверждают две последние версии Chrome/Edge/Firefox, публичный HTTPS, большую аварийную БД и нагрузку с конкурирующими записями. Эти ограничения сохраняются в отчёте.
