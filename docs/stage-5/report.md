## №23. Измеримая оптимизация

Стенд: Apple M1 Pro, 16 ГБ RAM, macOS, Node.js 24.21.0, PostgreSQL 16 в Docker Desktop. API запущен отдельно на loopback, пул 10 соединений. Для каждой версии создана отдельная БД с ровно 10 000 заявок, 50 различными пользователями. 50 параллельных исполнителей используют свои сессии и проверяют владельца/ответ. Вход исключён из измерения. Прогрев — 100 запросов, затем три серии по 1 000, список и карточка поровну. Данные проанализированы PostgreSQL ANALYZE. Сценарии запускались последовательно без параллельной сборки.

Узкое место: список автора сортировал все его примерно 200 строк перед LIMIT 20. Индекс миграции 000008 `(employee_id, created_at DESC, id DESC)` позволяет читать уже упорядоченные строки и остановиться после 20. Ответ, права и пагинация сохранены. Кэш не вводился: проблема решается индексом без риска устаревания.

Результаты одной контрольной пары запусков (серии 1/2/3):

- До: p95 списка **62,513 / 57,165 / 71,190 мс**, карточки **64,048 / 47,457 / 62,295 мс**.
- После: p95 списка **54,102 / 45,469 / 60,131 мс**, карточки **49,071 / 49,902 / 49,442 мс**.
- Во всех сериях по 1 000 запросов, **ошибок 0**; NFR-01 p95 ≤2 с выполнен в измеренной области.
- Среднее Execution Time SQL по 10 EXPLAIN ANALYZE после двух прогревов: **1,8974 → 0,1001 мс**, около **19 раз**. После исчезла сортировка списка, используется новый индекс. HTTP включает другие SQL, очередь пула и обработку; 19-кратное ускорение всего API не заявляется.

Нагрузка проверяет чтение списка/карточки, без браузерного рендера, внешней сети и одновременных записей. Очередь согласований покрыта функциональными тестами, отдельная нагрузочная серия очереди не проводилась. Вывод не переносится автоматически на другой сервер. Скрипт: `scripts/benchmark.mjs`; исходные метрики/планы: `output/stage-5/benchmark-{before,after}.json`.

## №24. Рефакторинг

Проблема — повторявшаяся сборка условий списка в `request.repository.ts` и `admin.repository.ts`. До каждый метод добавлял SQL/параметры статуса, дат и смещения независимо. После общий `repositories/request-filters.ts` строит типизированные условия с фиксированными SQL-выражениями и bound-параметрами. Владение/область доступа по-прежнему задаёт вызывающий репозиторий. HTTP-значения не становятся именами таблиц/столбцов.

Новые каталоги следуют существующим слоям routes → controllers → services → repositories; Zod находится в validators, транзакция открывается сервисом. Frontend использует отдельный компонент `admin-catalogs.tsx` и страницу `/admin/catalogs`, общий layout/навигацию. Дополнительный контейнер зависимостей или универсальный CRUD-фреймворк не нужен для двух небольших справочников.

Правила сохранены: kebab-case файлов, camelCase функций, TypeScript для приложения, SQL отдельно в миграциях/репозиториях, единый Prettier. Проверки типов, форматирования, production-сборки и прежние регрессии прошли. Общая типизация всех прежних SQL-ответов не переписывалась.

## №26. Развёртывание учебной версии

Среда — локальный Docker Compose: браузер → web:3000 → API:4000 → PostgreSQL:5432 (для локальных инструментов опубликован5433). API не публикует отдельный порт в профиле app. Это разрешённый заданием контейнерный учебный стенд, публичный хостинг не используется.

Последовательность: backup → миграции 7/8 → проверка версии → production-сборка API/Next.js и Docker → `make app` → readiness, спецификация, мониторинг. Старые бизнес-данные сохраняются. Миграции up/down/up проверены на восстановленной копии схемы 6: прежние поля всех 15 таблиц совпали. Скрипт `verify-upgrade.mjs` отказывается брать backup неподходящей версии.

Доступ ограничен серверными ролями/владельцем, сессии HttpOnly/SameSite=Lax, пароль scrypt, Origin проверяется, приложение использует DML-роль. Конфигурация из `.env`, backup исключены из Git. Внешний HTTPS отсутствует; до сетевого размещения нужны TLS, COOKIE_SECURE=true и точный APP_ORIGIN.

Откат: исходная предыдущая версия `1cd56b6` совместима с добавленными столбцами/индексом; можно пересобрать прежний код, сохранив схему 8. Down 7 теряет настройки активности/версии и проверялся только на копии. Восстановление backup требует учитывать изменения после копии. На рабочей БД down/reset не выполнялись. Порядок обновления/отката — [runbook](../runbook.md).

## №27. CI/CD

`.github/workflows/checks.yml`: push/PR/manual → checkout → Node24/npm ci → Prettier → TypeScript → PostgreSQL/миграции/роль → SQL → 37 тестов с покрытием → production-сборка → архив API/web/OpenAPI. Ошибка любого шага останавливает следующие; контейнеры очищаются always. Actions закреплены SHA, permissions contents:read, артефакт хранится 7 дней.

В CI создаётся `.env` с явно синтетическими паролями одноразовой учебной БД. Рабочие секреты не загружаются. Для будущего внешнего CD применять GitHub Secrets/Environment и ограниченные права среды. Автодоставка в чужой/публичный сервер не настроена; локальный выпуск выполняет `make app`.

Фактические запуски и Git-версии фиксируются в [ci-runs.md](ci-runs.md). YAML и локальное прохождение не считаются доказательством удалённого запуска. При падении открыть первый красный шаг, воспроизвести его команду локально, исправить причину и повторить весь pipeline; не обходить проверки для получения зелёного статуса.

## №28. Мониторинг и восстановление

`make monitor` опрашивает live/ready, фиксирует HTTP-статус, время, requestId, p95 и долю ошибок, возвращает ненулевой код при сбое. Длительность/статус каждого API-запроса пишутся JSON-логом; тело/пароли/cookie не журналируются. Это минимальный локальный мониторинг, без постоянного агента, ресурсных графиков и уведомлений.

`make verify-runtime` создал backup схемы 8, восстановил отдельную временную БД за **663,67 мс**, сравнил хэши/числа строк 15 таблиц и прочитал карточку сервисом приложения. Затем подключения только к копии ограничены до нуля; активные соединения копии завершены. Получено live=200/ready=503, monitor exit1; после возврата доступа live/ready=200, exit0. Рабочая БД не останавливалась.

Пример обезличенного успеха: `method=GET path=/api/health/ready status=200 durationMs=9`. Пример ошибки: `event=request_error code=53300 requestId=e4caf454-3de1-46ff-9f73-cf6697190442`; лог этого же запроса — status503/durationMs6. Секретов нет. По requestId связываются ответ мониторинга и журнал. Доказательство: `output/stage-5/runtime-check.json`.

Реакция: проверить live → ready → логи API по requestId → доступность PostgreSQL/версию схемы → устранить причину → повторить ready и чтение карточки. При потере данных восстановить backup в новую БД и проверить её перед переключением.
