# Тестирование на Jest

Тесты на TypeScript запускает Jest 30; ts-jest преобразует TypeScript в ESM. Конфигурация — `apps/api/jest.config.cjs`, проверка типов тестов — `tests/tsconfig.json`. Node.js запускается с `--experimental-vm-modules`, как описано в [документации Jest](https://jestjs.io/docs/ecmascript-modules). Предупреждение VM Modules ожидаемо; формат модулей приложения не менялся.

## Команды

Из корня проекта, после `npm ci`:

```bash
npm test                    # 9 проверок без БД; 27 интеграционных пропускаются
make test                   # все 36 проверок на отдельной временной БД
npm run test:coverage       # полный набор и покрытие, тоже на временной БД
npm run typecheck           # оба приложения и TypeScript тестов
```

Полный набор требует Docker/PostgreSQL, настроенный `.env` и роль приложения (`make setup`). Скрипт `scripts/test.mjs` создаёт `tripflow_test_*`, применяет миграции/SQL-проверки, передаёт её URL в Jest и удаляет только эту БД в finally. Перед первой записью API-тест сверяет имя подключённой базы. Рабочая БД тестами не меняется.

## Организация

- `validation.test.ts` — точные суммы и валидация.
- `auth-crypto.test.ts` — пароли, неверные и повреждённые хэши.
- `web-navigation.test.ts` — выбор рабочего раздела и безопасный адрес возврата.
- `openapi.test.ts` — внутренние ссылки и параметры контракта.
- `api.test.ts` и `helpers/` — настоящий Express/HTTP/PostgreSQL: роли, сессии, заявки, согласование, справочники, удаление сотрудников, отмена, конкуренция и журналирование.

Используются `describe`, `test`, `expect`, `beforeAll`/`afterAll`, `beforeEach` и `jest.spyOn`. Проверки ошибок SQL используют `rejects.toMatchObject`. Запросы отправляются встроенным fetch, БД не подменяется моками. Mock console.log убирает штатные HTTP-логи из вывода; отдельный сценарий перехватывает и проверяет содержимое журнала. Моки восстанавливаются между тестами.

Тесты API образуют последовательный сквозной сценарий: ранние шаги создают данные для следующих. Поэтому запуск — `--runInBand`, без `test.concurrent`/перемешивания. Для интеграции запускать весь `api.test.ts`, а не произвольный поздний шаг по имени. beforeAll открывает сервер/пул, afterAll закрывает их, вложенные группы готовят/очищают свои данные.

## Число тестов и покрытие

Jest показывает **5 наборов, 36 тестов**: 9 без БД и 27 интеграционных. Прежний `node:test` показывал 37, включая внешний тест-контейнер «API и PostgreSQL». В Jest контейнер стал `describe` и в число тестов не входит. Все 36 самостоятельных сценариев сохранены, их названия сверены с прежним набором.

Последний полный запуск: 36 успешно, ошибок/пропусков нет. Строки бизнес-модулей — **97,84%**, ветви — **96,70%**. Область: services/repositories/validators; demo-модули исключены, UI/контроллеры/middleware/crypto/CLI не входят. V8-покрытие рассчитывает Jest, поэтому проценты не сравниваются напрямую с прежним Node test runner.

Отчёты: `coverage/jest/index.html`, `lcov.info`, `coverage-summary.json`. При покрытии строк ниже 70% команда завершается ошибкой. Каталог coverage исключён из Git. GitHub Actions использует `npm run test:coverage`; материалы V этапа сохраняют исторические результаты прежних запусков.

## UI-тесты на Playwright

Отдельный набор в `tests/e2e/`, конфигурация `playwright.config.ts` в этой папке. Он дополняет 36 проверок Jest, а не заменяет их. Установить зависимости и браузер:

```bash
npm ci
npx playwright install chromium
# PostgreSQL и роль приложения должны быть подготовлены: make setup
npm run test:e2e             # также make test-e2e
npm run test:e2e:ui          # интерактивный интерфейс Playwright
npm run test:e2e:report      # открыть HTML-отчёт последнего запуска
```

На Linux/CI системные библиотеки и браузер устанавливаются командой `npx playwright install --with-deps chromium`.

### Стенд и сохранность данных

Playwright автоматически запускает `scripts/e2e-server.mjs` через [webServer](https://playwright.dev/docs/test-webserver). Скрипт создаёт свою `tripflow_test_e2e_*`, применяет миграции, готовит синтетические аккаунты и администратора. API работает на 127.0.0.1:4115, frontend — на 127.0.0.1:3115. Источник подключения заменяется на временный до импорта приложения; роль API остаётся trip_app_rw.

Frontend запускается из временной копии исходников внутри `output/playwright/runtime-*`: его кеш, dev-lock и сгенерированные типы не изменяют `apps/web`. Тесты могут идти параллельно с рабочим Docker-приложением или make dev. Порты 3115/4115 должны быть свободны. `reuseExistingServer=false`: готовый чужой сервер не используется, адрес рабочей БД для тестов не настраивается.

Входы и бизнес-действия выполняются через интерфейс, без подмены HTTP-ответов и прямого создания заявок через API в тестах. Каждый тест получает отдельный браузерный контекст; для других ролей создаются дополнительные контексты. Имена создаваемых объектов уникальны. Workers=1, автоматических повторов нет: падение не скрывается повторным успешным запуском.

При завершении/обычном Ctrl+C останавливаются дочерние процессы, закрывается пул, удаляются только временная БД и копия frontend. После SIGKILL/аварии ОС автоматическая очистка не гарантируется: проверить свои оставшиеся `tripflow_test_e2e_*` и `output/playwright/runtime-*`, не затрагивая tripflow. Рабочие заявки/сотрудники тестами не удаляются. Тест удаления сотрудника выполняется исключительно над пользователем, созданным этим тестом в одноразовой БД.

### Девять сценариев

1. Защищённая страница → вход, неверный пароль, сохранение адреса возврата, выход.
2. Отказ обычному сотруднику при открытии административного раздела.
3. Обязательные поля, создание/редактирование черновика, точная смета 100,10 + 200,20 = 300,30, сохранение после reload, удаление черновика.
4. Сотрудник → менеджер → финансист: будущий этап не виден заранее, обработанное решение сохраняется, история и финальный статус доступны автору.
5. Отказ требует комментарий, последующий этап пропускается, автор видит причину.
6. Отмена до первого решения: обязательная причина, сохранение после reload, отсутствие заявки в очереди.
7. Администратор создаёт и изменяет сотрудника, сотрудник создаёт заявку, администратор удаляет его с заявкой; удалённая карточка недоступна.
8. CRUD/отключение справочников, запрет удаления используемого подразделения, скрытие отключённой категории у сотрудника, журнал действий.
9. Мобильный Chromium 360×800: вход, форма, карточка, возврат в список; горизонтального переполнения всей страницы нет.

Это Chromium desktop и эмуляция мобильного viewport, не испытания двух последних версий Chrome/Edge/Firefox и не физического телефона.

### Отчёт и CI

HTML-отчёт: `output/playwright/report/index.html`. При ошибке скриншот, `error-context.md` и `trace.zip` находятся в `output/playwright/results/`. Трассу открыть через `npx playwright show-trace <путь-к-trace.zip>`. В trace могут быть cookie и синтетические пароли тестового стенда; отчёты исключены из Git общим правилом output/.

GitHub Actions после Jest и сборки устанавливает Chromium и запускает `npm run test:e2e`. Отчёт/трассировки загружаются отдельным артефактом на 7 дней даже при падении. Изменённая конфигурация CI проверяется локально; удалённый запуск требует отправки изменений в репозиторий.
