# Запуск обновление и восстановление TripFlow

## Первоначальная подготовка

Нужны Docker с Compose, Node.js 24 и npm. Используется существующая БД `tripflow`; исходная миграция содержит это имя явно. При переносе на другое имя сначала нужно подготовить совместимое изменение этой настройки, не редактируя уже применённую историю.

1. Если `.env` ещё нет, скопировать `.env.example`. Существующий `.env` не перезаписывать.
2. Задать `POSTGRES_PASSWORD`, `TRIP_APP_RW_PASSWORD` и согласованный `DATABASE_URL` для локального backend. Спецсимволы пароля в URL должны быть URL-encoded. В контейнере используются отдельные PG-переменные, поэтому пароль там не собирается вручную в URL.
3. Выполнить `npm ci`, `make setup`.
4. Задать в `.env` `DEMO_PASSWORD` от 12 символов и выполнить `make demo`. Команда заменяет только исходные заглушки паролей и создаёт недостающих учебных пользователей; повторный запуск не меняет существующие реальные хэши. Шаблон создаётся только при отсутствии активного маршрута подразделения.
5. Выполнить `make app`, открыть http://localhost:3000.

Учебные пользователи: `maxim@example.test` — сотрудник; `manager@example.test` — первый согласующий; `finance@example.test` — второй согласующий. Пароль — значение DEMO_PASSWORD на момент первоначального создания хэшей. Учебные данные предназначены для локального стенда.

В текущем подготовленном стенде первоначально использован учебный пароль `TripFlow-demo-2026!`.

## Локальная разработка

После `make setup` и `make demo` выполнить `make dev`. Frontend работает на localhost:3000, API — на 4000. Перед этим остановить контейнеры web/api, если они уже используют порт 3000:

```bash
docker compose --profile app stop web api
make dev
```

В режиме разработки разрешены `localhost` и `127.0.0.1` на портах 3000 и 3001. Если порт 3000 занят Docker, Next.js автоматически выбирает 3001 — вход продолжит работать. В production Origin должен точно совпадать с APP_ORIGIN. Для другого адреса изменить APP_ORIGIN и перезапустить API.

## Проверки

```bash
npm run typecheck
npm run build
npm run format:check
make check
make test
curl http://localhost:3000/api/health/live
curl http://localhost:3000/api/health/ready
docker compose --profile app ps
```

`make check` использует исходную тестовую заявку с id=1. SELECT Q-01–Q-04 показывают данные для сравнения; Q-05–Q-08 автоматически ожидают нужные исключения PostgreSQL и откатывают изменения. SQL-проверки не предназначены для пустой БД без seed-набора.

`make test` создаёт БД `tripflow_test_<время>`, применяет миграции и выполняет API-тесты под trip_app_rw; затем удаляет только эту временную БД. Рабочие заявки не меняются. Нужны запущенный PostgreSQL, установленные npm-зависимости и предварительно выполненный `make provision`. `npm test` без TEST_DATABASE_URL выполняет модульные проверки, а интеграционный блок пропускает; для полной проверки используйте `make test`.

## Обновление

1. Сохранить проверенную предыдущую версию исходников и версии/идентификаторы Docker-образов. В этой рабочей папке исходно не было Git-репозитория; тег предыдущего релиза нельзя подменять вымышленным значением.
2. Выполнить `make backup`, сохранить путь к копии.
3. Получить согласованную новую версию кода из командного репозитория.
4. Выполнить `npm ci`, `make migrate`, при изменении пароля — `make provision`.
5. Выполнить `make app` и smoke-проверку: вход, прежняя карточка, новый черновик, отправка, решения согласующих, история.
6. При необходимости подготовить демонстрационные данные отдельной командой `make demo`; это не часть обычного перезапуска.

`make up` запускает только БД; `make app` — всё приложение. `make app` не применяет миграции автоматически и не сбрасывает данные. `make reset` и откат seed-миграции для обновления не используются.

## Откат

Миграция маршрутов расширяет схему и не переписывает прежние заявки. Для совместимого предыдущего приложения предпочтителен возврат к проверенному коду/образу с сохранением расширенной схемы. Если предыдущий код не совместим с новыми статусами или маршрутами, требуется отдельный план и восстановление проверенной копии.

Down-миграции существуют для контролируемых проверок на копии. Откат `000004` удаляет шаблоны и ссылки, откат `000003` удаляет сессии. Применять их к рабочему стенду без анализа потери этих данных нельзя. Практический откат между двумя помеченными Git-релизами ещё нужно зафиксировать после подключения командного репозитория.

## Резервная копия и восстановление

```bash
make backup
make restore FILE=backups/имя.dump DB=tripflow_restore_demo
```

Копия создаётся через pg_dump в custom-формате, без владельцев и ACL. Файл закрыт от других локальных пользователей и исключён из Git. Хранить его отдельно от исходников: он содержит учебные данные и хэши.

Восстановление разрешено только в новую БД с префиксом `tripflow_restore_` или `tripflow_test_`. Существующая БД не перезаписывается. Техническая роль trip_app_rw должна быть заранее создана миграциями и настроена через provision; восстановление возвращает ей DML-права в копии. pg_dump одной БД не является резервной копией ролей всего кластера.

После восстановления проверить количество заявок/истории, связи и карточку через API, подключённый к копии. Для полного запуска копии указать её в DATABASE_URL отдельного API-процесса. Строку подключения не помещать в отчёт. Контролировать время восстановления по NFR-09 — до 30 минут.

## Диагностика и учебный отказ

1. Проверить `docker compose --profile app ps` и `/api/health/live`.
2. Проверить `/api/health/ready`: ошибка при живом процессе обычно означает проблему подключения или схемы.
3. Посмотреть `docker compose logs --tail=50 api` и `docker compose logs --tail=50 db`. API пишет время, метод, путь, HTTP-код, длительность и requestId; секреты и тела заявок в журнал не включаются.
4. Для учебного отказа остановить только db: `docker compose stop db`. Проверить, что live остаётся 200, а ready возвращает 503, и найти соответствующий requestId в журнале.
5. Вернуть БД: `docker compose up -d db --wait`. Повторить ready и вход/чтение карточки. При необходимости выполнить `docker compose restart api`.

Тест отказа выполнять на учебном стенде, когда никто не вводит данные. Volume сохраняется. Обычная остановка не является удалением БД.
