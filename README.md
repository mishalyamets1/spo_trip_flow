# TripFlow

Учебная система заявок на командировки: Next.js/React + Express + TypeScript + PostgreSQL 16.

Приложение позволяет сотрудникам оформлять поездки, согласующим принимать решения, а администратору управлять сотрудниками, заявками и маршрутами. Используется существующая схема этапа I; данные обновляются миграциями без пересоздания БД. Текущая схема — **8**, версия контракта API — **0.5.0**.

## Возможности

- Создание и редактирование черновика, смета с серверным расчётом суммы, отправка и история заявки.
- Последовательное согласование, отказ с причиной, вкладки ожидающих и обработанных решений.
- Отмена собственной отправленной заявки до первого решения согласующего.
- Поиск, фильтры и пагинация списков с сохранением параметров в URL.
- Админка: сотрудники, роли, блокировка, все заявки, административная отмена, замена согласующих, маршруты и журнал действий.
- Управление подразделениями и категориями расходов: создание, изменение, отключение и удаление неиспользуемых значений.
- Полная хронология решений, включая промежуточные этапы без изменения общего статуса.
- Удаление сотрудника вместе со всеми созданными им заявками с сохранением его решений в чужих заявках.

## Быстрый старт

Нужны Node.js 24, npm и Docker Compose. Если `.env` уже есть, не перезаписывайте его.

```bash
cp .env.example .env  # только при первом запуске
# Задайте пароли в .env, включая DEMO_PASSWORD и ADMIN_PASSWORD.
# Согласуйте DATABASE_URL с TRIP_APP_RW_PASSWORD и POSTGRES_PORT.
npm ci
make setup
make demo
make admin
make app
```

Открыть **http://localhost:3000**. Для обычного повторного запуска подготовленного проекта достаточно `make app`.

Настройки в `.env`:

- `POSTGRES_PASSWORD` — пароль владельца БД для подготовки и миграций.
- `TRIP_APP_RW_PASSWORD` и `DATABASE_URL` — доступ API к БД; URL использует опубликованный `POSTGRES_PORT`.
- `DEMO_PASSWORD` — начальный пароль учебных сотрудника и согласующих, от 12 символов.
- `ADMIN_EMAIL` — почта первого администратора, по умолчанию `admin@example.test`.
- `ADMIN_PASSWORD` — начальный пароль администратора, от 12 символов. Если он не задан, `make admin` использует `DEMO_PASSWORD`.

## Вход и роли

Страница входа: **http://localhost:3000/login**. Авторизация построена на серверных сессиях PostgreSQL и HttpOnly cookie со сроком 8 часов. Выход завершает серверную сессию.

Учебные пользователи:

- `maxim@example.test` — сотрудник.
- `manager@example.test` — первый согласующий.
- `finance@example.test` — второй согласующий.
- `admin@example.test` — администратор, если при создании не задан другой `ADMIN_EMAIL`.

Пароль задаёт DEMO_PASSWORD при первом создании хэшей. В подготовленном локальном стенде использован `TripFlow-demo-2026!`. Повторный `make demo` не сбрасывает уже установленные хэши.

**Для администратора текущего стенда пароль находится в `.env`, поле `ADMIN_PASSWORD`.** Он отличается от учебного пароля остальных пользователей. Повторный `make admin` не меняет существующий аккаунт и пароль; редактирование переменной в `.env` также не сбрасывает пароль в БД.

Роли определяют права и могут совмещаться:

- `EMPLOYEE` — собственные заявки.
- `APPROVER` — решения по назначенным этапам согласования.
- `ADMIN` — управление системой через `/admin/*`.

Пользователю только с APPROVER открывается согласование, только с ADMIN — админка. Учебные менеджер и финансист имеют EMPLOYEE + APPROVER, поэтому видят и свои поездки, и согласование чужих.

## Работа с заявками

Маршрут по умолчанию: руководитель → финансы. Сотрудник создаёт черновик, сохраняет его и отправляет; согласующие входят каждый под своей учётной записью и принимают решение по очереди. Исходная заявка этапа I сохраняет свой прежний маршрут из одного шага.

В разделе «Согласование» вкладка «Ожидают решения» содержит только текущие этапы, «Обработанные мной» — ваши прежние решения с датой и комментарием. Общий статус заявки показан отдельно: решение руководителя ещё не означает окончательное согласование финансистом. Отменить свою отправленную заявку можно в карточке с обязательной причиной; после первого решения это действие недоступно.

Назначенные карточки доступны согласующему по прямой ссылке; доступ к данным проверяет API. Самосогласование запрещено: для собственной поездки менеджера или финансиста нужен маршрут его подразделения без него самого.

## Администрирование

Панель: **http://localhost:3000/admin/employees**. Доступна только роли ADMIN.

- **Сотрудники:** создание учётных записей, редактирование профилей, назначение ролей и блокировка с завершением сессий.
- **Все заявки:** просмотр смет и истории любых сотрудников, отмена незавершённой заявки и замена согласующего первого ожидающего этапа с обязательной причиной.
- **Маршруты:** настройка последовательности согласующих по подразделениям. Отправленные заявки сохраняют прежние этапы.
- **Журнал действий:** кто, когда и по какой причине изменил данные или доступ.

Удаление сотрудника удаляет все его заявки независимо от статуса, их поездки, сметы, этапы и историю, затем профиль и учётную запись. Перед удалением показывается число заявок; требуются причина и подтверждение табельным номером. Если есть ожидающие чужие этапы или назначения в шаблонах, необходимо выбрать замену. Принятые решения в чужих заявках сохраняются с именем удалённого сотрудника.

Для сохранения данных сотрудника вместо удаления можно отключить вход. Собственную учётную запись администратора нельзя удалить, отключить или лишить ADMIN. Подробные правила — в [инструкции админки](docs/admin.md).

## Обновление существующего стенда

```bash
npm ci
make backup
make migrate
make migrate-status
make admin             # если первый администратор ещё не создан
make app
```

`make app` сам миграции не применяет. `make demo` при обычном обновлении не требуется. Порядок резервного копирования и восстановления описан в [runbook](docs/runbook.md).

## Разработка и проверки

```bash
docker compose --profile app stop web api
make up                     # PostgreSQL остаётся в Docker
make dev                    # web :3000 и api :4000 запускаются локально
```

`make app` запускает все три сервиса в Docker; `make dev` запускает web/API на компьютере и использует ту же БД. Перед сменой режима остановите web/API предыдущего запуска. Если Next.js выбрал порт 3001, используйте адрес, указанный в терминале.

Проверки выполняются из корня проекта при запущенной БД:

```bash
npm run typecheck
npm run build
npm run format:check
make check                  # исходные SQL-проверки Q-01–Q-08
make test                   # Jest: API и БД, отдельная временная база
npm run test:coverage       # Jest и покрытие бизнес-модулей, временная БД
```

`make test` создаёт отдельную временную БД, применяет миграции и после проверок удаляет её; рабочие данные не меняются. `npm test` без TEST_DATABASE_URL пропускает интеграционный блок; полная проверка — `make test`. Тесты написаны на TypeScript с Jest и ts-jest: `describe`/`test`, `expect`, хуки и `jest.spyOn`. Полный запуск — 36 тестов; покрытие бизнес-модулей — 97,84% строк. [Устройство тестов и команды](docs/testing.md), [протокол проверок](docs/verification.md).

## Команды окружения

- `make up` / `make down` — запустить БД / остановить всё окружение.
- `make setup` — поднять БД, применить миграции, настроить пароль роли приложения.
- `make migrate` / `make migrate-status` — обновить / проверить версию схемы.
- `make provision` — настроить пароль trip_app_rw из окружения.
- `make admin` — создать первого администратора; почта по умолчанию `admin@example.test`, пароль из `ADMIN_PASSWORD` (либо `DEMO_PASSWORD` для учебного стенда).
- `make app` — собрать и запустить web/api/db; миграции предварительно выполнить отдельно.
- `make backup` — резервная копия в игнорируемый каталог backups.
- `make restore FILE=... DB=tripflow_restore_demo` — восстановить в отдельную новую БД.
- `make psql` — SQL-консоль.

`make reset` удаляет volume; `make migrate-down` откатывает последнюю миграцию. Для обычного запуска, обновления и восстановления эти команды не нужны.

## Структура

```text
apps/web/              интерфейс Next.js
apps/api/src/          Express, сессии, валидация и операции с БД
apps/api/Dockerfile    контейнер API
apps/web/Dockerfile    контейнер frontend
scripts/              миграции, backup/restore и тестовое окружение
tests/                проверки API, транзакций, доступа и валидации
database/migrations/  история схемы 000001–000006
docs/api/             OpenAPI 3.1
docs/decisions/        архитектура, ER-дополнение, статусы и принятые решения
docs/stage-2/          материалы работ №5–8
docs/stage-3/          материалы работ №9–14
docs/stage-4/          материалы работ №15–22 и макеты
```

Backend внутри `apps/api/src` разделён на слои:

- `routes/` — URL и HTTP-методы.
- `controllers/` — входные HTTP-данные и ответы.
- `services/` — бизнес-правила и транзакции.
- `repositories/` — SQL и доступ к PostgreSQL.
- `middlewares/` — сессии, Origin, логирование и обработка ошибок.
- `validators/` — Zod-схемы запросов.
- `types/` — общие типы данных.
- `utils/` — хэширование паролей и токенов.

Пример операции: `request.routes.ts` → `request.controller.ts` → `request.service.ts` → `request.repository.ts`. `app.ts` только собирает Express-приложение. Подключение и механизм транзакций находятся в `db.ts`; бизнес-сервис передаёт один transaction client всем участвующим репозиториям.

Frontend внутри `apps/web` использует файловый роутинг Next.js App Router:

- `/login` — вход с возвратом на запрошенную страницу.
- `/requests` — список; фильтры `status`, `from`, `to` и `page` находятся в URL.
- `/requests/new` — создание черновика.
- `/requests/[id]` — карточка с историей и действиями.
- `/requests/[id]/edit` — редактирование собственного черновика.
- `/approvals` — очередь согласующего; `view=processed` — обработанные решения, `decision`, `from`, `to`, `page` — фильтры и страница.
- `/admin/employees`, `/admin/requests`, `/admin/routes`, `/admin/catalogs`, `/admin/audit` — сотрудники, все заявки, маршруты и журнал; доступ только ADMIN.

В `app/` находятся страницы, layouts, loading/error и 404. Компоненты сгруппированы в `components/auth`, `components/layout`, `components/requests`, `components/approvals`, `components/admin` и `components/ui`. Сессией управляет `providers/auth-provider.tsx`, повторяющиеся запросы и действия вынесены в `hooks/`, методы API — в `services/`, типы — в `types/`, форматирование и HTTP-клиент — в `lib/`.

Карточки открываются по прямым ссылкам; обновление страницы сохраняет адрес, а Back/Forward работают через браузерную историю. Неавторизованный пользователь переходит на `/login?next=...`. UI проверяет сессию на клиенте; доступ к данным и операциям по-прежнему контролирует backend.
